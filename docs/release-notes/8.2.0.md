### `Jedis(URI, JedisClientConfig)` applies `SslOptions` for `rediss://` URIs ([#4706](https://github.com/redis/jedis/pull/4706))

The URI constructor rebuilds the config around the URI and copied the legacy `sslSocketFactory`,
`sslParameters` and `hostnameVerifier` settings, but not `SslOptions`. A truststore, client
keystore or `SslVerifyMode` configured through `SslOptions` was silently dropped: the connection
fell back to `SSLSocketFactory.getDefault()`, so a pinned private CA widened to the JVM `cacerts`
trust and no client certificate was presented for mTLS. The same config passed to
`Jedis(HostAndPort, JedisClientConfig)` already honoured it.

`SslOptions` is now carried over when the URI scheme is `rediss://`. The scheme stays authoritative
for TLS, as the constructor documents: with `redis://` the connection remains plaintext and
`SslOptions` on the config is ignored, so a config shared between TLS and non-TLS endpoints does not
turn a plain URI into a TLS handshake.

**Action required:** none for correctly configured applications. A `rediss://` connection that only
succeeded because the configured truststore or client certificate was ignored now uses them, so
check that the `SslOptions` on the config match the server.
