# Jedis 8.1.0 Release Notes

This guide helps you upgrade from Jedis 8.0.0.

!!! warning "Unreleased"
    Jedis 8.1.0 has not been released yet. These notes track changes on `master`
    since 8.0.0 and are updated as changes merge; remove this notice when 8.1.0
    ships.

!!! note
    If your change alters user-visible behavior, add an entry here in the same PR.

## Highlights

### Smart Client Handoffs ([#4668](https://github.com/redis/jedis/pull/4668))

Jedis now reacts to server maintenance push notifications with relaxed timeouts and pre-handoffs.
The feature requires RESP3 and is configured with `MaintenanceNotificationsConfig` via
`RedisClient.builder().maintenanceNotifications(...)`. It is enabled by default (`Mode.AUTO`) on
RESP3 connections; pass `MaintenanceNotificationsConfig.DISABLED` to opt out. See the
[Smart Client Handoffs guide](../smart-client-handoffs.md).

### Capacity hints for collection-built commands ([#4737](https://github.com/redis/jedis/pull/4737))

`CommandArguments` gained `ensureCapacity(int)`, a chainable hint that pre-sizes the backing
argument list for the expected total number of arguments (command token included — the RESP
array length of the final command):

```java
CommandArguments args = new CommandArguments(ZADD)
    .ensureCapacity(2 + 2 * members.size()) // command + key + member/score pairs
    .key(key);
```

This avoids repeated `ArrayList` growth copies when large commands are built directly, e.g.
via `executeCommand`. Under-estimating falls back to normal growth, so correctness never
depends on the estimate. The typed API benefits automatically: collection-built commands
(`MSET`, map `HSET`/`HMSET`, `ZADD`, `GEOADD`, `XADD`, `addObjects(...)`) now pre-size
internally from the known collection size.

## API Additions

### Vector set plain overloads ([#4693](https://github.com/redis/jedis/pull/4693))

Parameter-free overloads for the experimental vector-set methods that previously required `null`
params: `vadd`/`vaddFP32` with `reduceDim`, and the `vsim*WithScores` and `vsim*WithScoresAndAttribs`
variants, across the String, binary, and pipeline APIs.

## Behavior Changes

Changes that may affect existing applications even though they are
not breaking API changes.

### Closing a client no longer stops its `AuthXManager`

An `AuthXManager` is created by the application and passed in through `JedisClientConfig`, so its
lifecycle now belongs to the application, like the config itself. Previously `ConnectionPool.close()`
stopped the manager unconditionally, which broke every other user of a shared manager: after a
Sentinel master failover the new master pool was left without token renewal, and closing one of
several clients built on the same manager stopped renewal for the rest. Cluster and multi-db clients,
on the other hand, never stopped it. All clients now behave the same and leave the manager running.

Closed and destroyed pools are also properly unregistered from the manager. Previously the
unregistration silently failed, so a stale pool kept receiving post-authentication callbacks and
made the token manager's renewal cycle fail on its closed pool.

**Action required:** call `authXManager.stop()` after closing the last client that uses it.
Applications that relied on `RedisClient.close()`, `JedisPooled.close()` or
`RedisSentinelClient.close()` to stop the manager will otherwise keep its renewal threads alive.

### Key pre-processor applied to all key arguments ([#4675](https://github.com/redis/jedis/pull/4675))

The source key of `ZRANGESTORE`/`GEOSEARCHSTORE` and the script `KEYS` passed to
`eval(script, keyCount, ...)` / `evalsha(sha1, keyCount, ...)` were previously not
treated as keys: a configured `CommandKeyArgumentPreProcessor` (e.g. key prefixing)
did not transform them, and the store commands' source key was invisible to cluster
key routing. They are now handled like every other key argument: the pre-processor
applies to them, and on cluster a cross-slot `ZRANGESTORE`/`GEOSEARCHSTORE` fails
client-side with `JedisClusterOperationException` instead of the server's CROSSSLOT
error.

**Action required:** remove any manual prefixing workaround for these arguments
(they would now be prefixed twice), and update `catch` blocks that matched the
server CROSSSLOT `JedisDataException` for these commands.

### Pub/sub push messages are no longer delivered as command replies outside a subscription ([#4701](https://github.com/redis/jedis/pull/4701))

On RESP3, a pub/sub push frame that arrived while no pub/sub read loop was running —
for example a `message` the server delivered after the `UNSUBSCRIBE` confirmation,
as can happen behind the Redis Enterprise proxy — was returned as the next command's
reply. This desynced the reply stream and typically surfaced as
`ClassCastException: java.util.ArrayList cannot be cast to [B`.

Such stray pub/sub pushes are now logged at debug level and dropped instead of being
delivered to the application, and the following command receives its own reply.
Behavior during an active `subscribe`/`psubscribe`/`ssubscribe` loop is unchanged.
Custom `PushConsumer`s registered on a connection now also observe pub/sub-typed
pushes received outside a subscription, which the built-in consumer previously
propagated before they could see them; the public `PUBSUB_CONSUMER` constant is
unchanged and still propagates unconditionally.

**Action required:** none for typical applications. Code that relied on reading raw
pub/sub frames from a connection without going through the `JedisPubSub`/
`JedisShardedPubSub` loops (e.g. hand-rolled `sendCommand(SUBSCRIBE)` +
`getUnflushedObject()`) will no longer receive those frames; use the pub/sub APIs or
register a custom `PushConsumer` that propagates them.

### Pipeline `sync()` reports read failures to the caller ([#4761](https://github.com/redis/jedis/pull/4761))

**Before:** if a node's connection failed while `ClusterPipeline.sync()` was reading replies, the
error was only logged. `sync()` returned normally, `Response.get()` for that node threw
`IllegalStateException: Please close pipeline or multi block before calling this method`, and the
next command routed to the node, or `close()`, could throw `NullPointerException`. Single-node
`Pipeline.sync()` threw the error, but left its responses unset in the same way.

**Now**, on both pipelines:

- `sync()` and `close()` rethrow the failure unchanged. A cluster pipeline still reads every other
  node first; if several nodes fail, the first in pipeline order is thrown and the others are
  attached as suppressed.
- Each response whose reply was lost rethrows the failure from `get()`: a `JedisException` (such as
  `JedisConnectionException`) as is, anything else as the cause of a `JedisException`.
- A cluster pipeline drops the failed nodes, so it can be closed or reused; the next command for such
  a node takes a fresh connection. A single-node pipeline's connection is broken after a failed
  `sync()`, so close it.

The pipeline does not refresh the slot cache: after a failover, a reused cluster pipeline keeps
routing to the old address until the topology is refreshed elsewhere.

**Action required:** handle exceptions from `ClusterPipeline.sync()`/`close()`, which previously
returned normally after a failed read. Don't re-send a failed pipeline blindly: the server may
already have applied some of its commands.

### `ClusterPipeline` and `JedisCluster` built from a `JedisClientConfig` honour its command settings

The `commandKeyArgumentPreProcessor`, `jsonObjectMapper` and `searchDialect` carried by a
`JedisClientConfig` were applied by `RedisClusterClient`, but ignored by the `ClusterPipeline`
constructors that take a `JedisClientConfig` and by the deprecated `JedisCluster(Set<HostAndPort>,
JedisClientConfig, ...)` constructors, which built their command objects from the config's protocol
settings alone. With a key-prefixing pre-processor, a pipeline or `JedisCluster` created from the
same config as a `RedisClusterClient` sent its keys un-prefixed, so its reads and writes landed
outside the configured namespace. These constructors now apply the three settings exactly as the
builder-based clients do.

**Action required:** remove any manual key prefixing or JSON pre-serialisation that compensated for
this in code using these constructors; it would now be applied twice.
